# Разработка ads-telegram-mcp

Пользовательская инструкция находится в [README](../README.md).
Здесь описаны устройство сервера, добавление инструментов и локальные проверки.

Сервер использует официальный MCP Python SDK 2.x (`MCPServer`).
Инструменты обращаются к Telegram Ads через синхронный клиент TeleAd.

## Сборка сервера и настройки

`create_server(settings: Settings)` принимает готовые настройки.
В точке запуска вызывается `create_server(settings=Settings())`.
`register_tools` передаёт сервер и `TeleAdRunner` модулям областей.
Каждый модуль регистрирует функции декоратором `@server.tool(...)`.
Регистрация инструментов не выполняет запросов к API.

stdout занят протоколом MCP, сообщения SDK идут в stderr.
Альтернативная точка запуска — `uv run --locked python main.py`.

`Settings` использует `pydantic-settings`. Путь к `.env` вычисляется
относительно модуля `config.py`, поэтому не зависит от текущего рабочего каталога.
Файл читается в UTF-8; посторонние ключи игнорируются.

Приоритет источников:

1. Явные аргументы `Settings(...)`.
2. Переменные окружения с префиксом `TELEGRAM_ADS_`.
3. `.env` в корне проекта.
4. Значения полей по умолчанию.

Пустая переменная окружения тоже перекрывает `.env`. Пробелы по краям значений
удаляются; пустой `account_id` становится `None`. Модель настроек неизменяема,
поле токена исключено из repr и сериализации.
Для изоляции проверок от локального `.env` передавайте `Settings(_env_file=None, ...)`.

Без токена сервер запускается и отдаёт `tools/list`; вызов API-инструмента
возвращает MCP tool error с именем недостающей переменной.
Браузерная сессия Telegram Ads не авторизует API-клиент.

Для новой области добавьте `tools/budgets.py`, `audiences.py`
или `pixel.py` с `register(server, runner)` и включите модуль
в реестр. Внутри регистрируйте функции с явными Python-параметрами через
`@server.tool(...)`; вызывайте методы клиента через `await runner.run(operation)`.
`TeleAdRunner.run` принимает синхронную функцию `Client -> T` и возвращает `T`
без преобразования моделей в словари. Для короткого вызова подойдёт lambda,
для нескольких API-вызовов и обработки результатов — обычная функция.

```python
from mcp.server import MCPServer
from telead import Client
from telead.models import Ad

from ..execution import TeleAdRunner
from .common import READ_ONLY


def register(server: MCPServer, runner: TeleAdRunner) -> None:
    @server.tool(annotations=READ_ONLY)
    async def list_active_ads() -> dict:
        """Get active ads from the token owner's account.

        Only the first 20 ads are inspected.
        """
        def load(client: Client) -> list[Ad]:
            account = client.get_current_account()
            page = client.get_ads_list(account_id=account.account_id, limit=20)
            return [ad for ad in page.ads if ad.status == "active"]

        ads = await runner.run(load)
        return {"ads": [ad.raw for ad in ads]}
```

Пример явно выбирает владельца токена и обрабатывает одну страницу объявлений.
Он иллюстрирует расширение сервера и не входит в текущий набор инструментов.

`TeleAdRunner` создаёт один Client на всю операцию и закрывает его по её
завершении, включая ошибку. Операция целиком выполняется в рабочем потоке:
цикл MCP не блокируется, HTTP-сессии не разделяются между параллельными операциями.
Генераторы и итераторы TeleAd нужно прочитать внутри операции, пока Client открыт.
Составные операции вызывают методы Client и обычные функции обработки;
вызывать собственные MCP-инструменты через MCP внутри сервера не требуется.
MCP-инструмент формирует конечный ответ: использует `model.raw` для исходного
payload либо выбирает и агрегирует поля типизированных моделей. Сериализацию
ответа в JSON выполняет MCP SDK. Общего рекурсивного адаптера нет.
Реальные методы TeleAd доступны только из кода; универсального MCP-инструмента
для произвольного API-вызова нет.

Для изменения объявлений используется `WRITE_AD`; `READ_ONLY` предназначен
только для чтения. При добавлении операций записи явно опишите последствия
и передавайте стабильные idempotency keys там, где API их поддерживает,
для повторения одной бизнес-операции; автоключ TeleAd защищает только повторы
внутри одного вызова клиента. Сокращение ответов и выбор областей при запуске
можно добавлять на этих границах отдельно.

`READ_ONLY` содержит декларации поведения для MCP-клиента, а не ограничения
исполняемого кода.

## Ответы и ошибки

Базовые инструменты возвращают исходные ответы API из `model.raw`.
Массивы оборачиваются в `accounts`, `ads`, `stats` или `report`.
Новые поля API сохраняются. `get_ads_stats` возвращает агрегаты и, по запросу,
исходные строки статистики; его контракт описан ниже.

В базовых инструментах ошибки TeleAd преобразуются в MCP tool errors.
Операции создания и изменения объявлений сохраняют исход попытки записи
в результате, как описано ниже. Наружу не передаются
тела ошибочных ответов и транспортные сообщения. Для API-ошибок сохраняются
код и HTTP-статус. Timeout чтения 30 секунд, максимум один повтор средствами
TeleAd; для загрузки файлов TeleAd устанавливает timeout чтения не менее 120 секунд.
С учётом подключения и ожидания перед повтором весь вызов может длиться дольше.

Ограничение групповых запросов до 100 ID задано в схемах инструментов;
оно не означает, что такой же предел установлен Telegram API.
Явный `ToolError` из составной операции передаётся без замены.

## Составная статистика get_ads_stats

Операция `operations/ads_stats.py` получает готовый `Client` и возвращает
типизированный `AdsStatsBatch`. При непустом `ad_ids` она напрямую запрашивает
статистику выбранных ID, без предварительного получения списка объявлений.
Для пустого списка, `None` или пропущенного параметра получает все страницы
`get_ads_list` по 100 записей и собирает ID без фильтра по статусам.
ID обрабатываются в полученном порядке без удаления повторов.
Повтор курсора или пустая страница с непустым курсором прерывают операцию
ошибкой, чтобы неполный список не был принят за полный.

Для каждого ID последовательно вызывается `get_ad_stats`; все вызовы используют
один `Client` в одном рабочем потоке. Операция суммирует показатели
типизированных `AdStatItem`. Расход складывается через `Decimal`; преобразование
в JSON-число выполняется при формировании ответа инструментом.
Показатели разных валют внутри одного ряда не складываются.

При `include_timeseries=false` строки интервалов не сохраняются в результате
операции. `include_timeseries=true` сохраняет их для выдачи через `point.raw`.
Пустой ряд даёт `data_points=0` и `totals=null`, без предположений о валюте.
Непустой ряд с нулевыми показателями возвращает нулевые суммы.

Ошибки API отдельных объявлений и транспортные ошибки после повторов TeleAd
сохраняются в `AdStatsFailure`; следующие ID продолжают обрабатываться.
Ошибки авторизации, прав доступа и ограничения частоты запросов прекращают
всю операцию. Общая функция `public_error_message` в `execution.py` формирует
сообщения как для ошибок всего инструмента, так и для отдельных объявлений,
без тел ответов, транспортных подробностей и токена.

Инструмент возвращает округлённые `from_time` и `to_time`, `interval`,
`total_count`, `succeeded_count`, `failed_count`, `complete`, `ads` и `errors`.
Границы округляются до API-вызовов; пустой период после округления отклоняется.
`complete` равен `false`, если запрос статистики хотя бы одного ID завершился ошибкой.
Успешные элементы `ads` содержат `ad_id`, `data_points`, `totals` и необязательный
`stats`. В `errors` находятся `ad_id` и безопасное сообщение `error`.

## Справочники и разрешение площадок

`operations/targeting.py` возвращает последовательность типизированных моделей;
преобразование моделей в `raw` выполняется в `tools/targeting.py`.
`get_targeting_options` принимает только `catalog`: `languages`, `topics`
или `countries`. Выбранный справочник получается одним API-запросом
и возвращается целиком. Локации загружаются отдельным инструментом
`get_target_locations`, только когда нужны.

Для локаций обязательны `country_code` и непустой `query`: операция автоматически
обходит все страницы поиска с `limit=100`, передавая непрозрачные курсоры API.
Повтор курсора или пустая страница с курсором продолжения прерывают операцию
с ошибкой, чтобы не выдать частичный результат как полный.

Порядок API и повторяющиеся элементы сохраняются. Ответ `get_targeting_options`
содержит `catalog`, `options` и `total_count`. Ответ `get_target_locations` —
`locations` и `total_count`. В обоих случаях счётчик равен длине полученного списка;
внешних параметров пагинации нет. Некорректные значения параметров отклоняются
до HTTP-запроса.

Каждый вызов заново обращается к API: программного кэша и сохранения на диск нет.
В инструкциях сервера и описании инструмента модели рекомендовано повторно
использовать справочники из контекста или сохранённых результатов и обычно
обновлять их не чаще раза в неделю. Явный запрос на обновление или признаки
устаревших данных допускают повторную загрузку. Для локаций повторно используются
результаты той же страны и поискового запроса.

У справочников и `getTargetChannel`/`getTargetBot` нет параметра `account_id`.
В частности, `Client.with_account` или default account не подставляют его
в эти методы. Инструменты не обещают переключение на связанный аккаунт
и не выполняют дополнительные вызовы разрешения перед `create_ads`.

## Создание и загрузка медиа

Контракт и эффекты операций описаны в [ad-creation-design.md](ad-creation-design.md).
Схемы `NewAd` и таргетинга строгие и запрещают неизвестные поля. Весь список
валидируется MCP SDK до вызова функции инструмента. Таргетинг и расписание
дополнительно проверяются типизированными входами TeleAd.

В `dry_run` операция с клиентом не создаётся: токен и API не нужны.
Динамическую пригодность дат проверяет API, чтобы локальные часы не мешали
повтору с тем же ключом после наступления запланированного времени.

Операции записи сначала разрешают явный или настроенный аккаунт через
`get_accounts_by_id`; без него получают владельца токена через `get_current_account`.
Ответ без доступного ID и известной валюты прерывает операцию до записи.
Аккаунт определяется один раз на пакет и передаётся явно в каждый `create_ad`.
Ключи, порядок, повторяющиеся объявления и ID сохраняются.

`CreationBatch` содержит типизированные результаты с `Ad` или исключением;
преобразование в компактный ответ и безопасные сообщения выполняет MCP-инструмент.
Транспортные ошибки, серверные ошибки, запрос в процессе и неожиданный ответ
после попытки создания считаются неизвестным исходом, а не доказанным отказом.
Неожиданная ошибка также останавливает оставшиеся записи.

Фото проверяются Pillow по содержимому с декодированием. MP4 проверяется
локальным `ffprobe` с timeout 20 секунд и разрешённым протоколом `file`.
Временная копия для проверки содержит те же байты, которые затем отправляются
в API; исходный файл не читается повторно после проверки. Учитываются поворот
и соотношение сторон пикселя видео. Наличие `ffprobe` требуется только для MP4.

`create_ads` и `upload_media` имеют `read_only_hint=false`, а также
`idempotent_hint=false`. Для создания установлен `destructive_hint=true`
из-за возможного изменения бюджета и показов, для загрузки — `false`.
Идемпотентность создания обеспечивается ключом API и ограничена 24 часами;
загрузки такого механизма не имеют.

## Управление существующим объявлением

`tools/ad_management.py` регистрирует три одиночных инструмента:
`increase_ad_budget`, `edit_ad`, `submit_ad_for_review`. Входная модель
`AdChanges` содержит только редактируемые поля; таргетинга, размещения
и начального бюджета в ней нет. Неизвестные поля и пустые изменения запрещены.
Пропущенные поля и `null` не отправляются в API; `false`, `0` и допустимые
пустые строки сохраняются. `schedule=false` удаляет расписание, объект
преобразуется в `InputAdSchedule`. Совместимость с текущим состоянием объявления
и динамические ограничения проверяет API. Предварительного чтения объявления нет.

`operations/ad_management.py` разрешает аккаунт через `resolve_account`,
затем выполняет один вызов записи в том же Client. Операция возвращает
типизированный `AdChangeResult` с аккаунтом, исходом, `Ad` или исключением.
Сериализация и безопасные сообщения остаются в MCP-инструменте.
Ответ содержит `account_id`, `ad_id`, `currency`, `outcome` и `ad` либо `error`.
Пополнение также возвращает исходный `idempotency_key`.

Отказ API или локальная ошибка TeleAd дают `failed`. Транспортная ошибка,
серверная ошибка, запрос в процессе, неверный ID в успешном ответе
или неожиданное исключение после попытки записи дают `unknown`.
Ошибки разрешения аккаунта возникают до записи и передаются как tool errors.
Автоматических откатов, отправки на модерацию вслед за пополнением
или дополнительных записей нет.

Для пополнения обязателен непустой ключ длиной до 128 символов. Он передаётся
без замены в TeleAd и сохраняется при его внутренних повторах. Описание инструмента
требует повторять запрос с исходным ключом и параметрами в пределах 24 часов.
После неопределённого исхода редактирования или отправки на модерацию нужно
прочитать актуальные поля или статус. У этих двух методов ключа нет.
TeleAd допускает внутренние повторы редактирования как установки абсолютных
значений; отправку на модерацию не повторяет после транспортных/серверных ошибок
с неизвестным исходом. Ответ об ограничении частоты может быть повторён клиентом.

Все три инструмента имеют `read_only_hint=false`, `destructive_hint=true`
и `idempotent_hint=false`: они могут переводить деньги, включать показы,
снимать лимиты или запускать модерацию. Ключ пополнения ограничен сроком
хранения результата, поэтому инструмент не обещает неограниченную идемпотентность.

## Локальные проверки

Из корня проекта:

